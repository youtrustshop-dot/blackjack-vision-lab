## C. Data and boundary

The new generator produces 18 continuous videos from original owned artwork: six difficulty renderings each for development, validation and final holdout. Each partition has a different seed, session and font/paper/back family. Development and validation together represent **two physical sessions and 12 distinct rounds**; variants repeat the same hands and are paired, not independent sessions. All families share renderer/layout mechanics, so this is graphic transfer evidence, not independent provider-engine generalization.

The baseline reader receives RGB pixels, timestamps and initial ROIs only. Simulator phase, identity, future frames, truth and scenarios are evaluator-only. The sessions include immediate blackjack, hit/bust, stand/dealer draws, double, visible table clearing and identical card faces in distinct rounds. There are five player decision opportunities per rendering; immediate blackjack has no player decision. No split-hand vision was evaluated.

Manifests, source archive, generator and trace hashes are in [the JSON receipt](../validation/results/independent-tournament/local-baseline.json). Holdout video/truth content remains unexamined by the reader; the publication checks its manifest hash only. No synthetic pixels are presented as provider recordings. No provider/private screenshot was sent to a service.

## E. Failure interpretation

Clean validation isolates a material context/continuity gap: complete ranks can coexist with an unknown phase and a missing timely recommendation. Overlap still misses one development exposure; clean profiles have provisional ID switches despite correct final inventories. Rotation/fading fail the application objective. Unknown suits are abstentions, not wrong readings, but they preclude a claim of complete 52-card recognition for poker.

A card candidate, present unreadable card, present back and absent card are distinct. Publication independently checks development/validation truth/video hashes and distinguishes unreadable face-up cards from backs. The inherited exact-table metric could incorrectly accept an unreadable face-up card classified as a back; a derived metric fixes that condition from preserved traces. On these traces the correction changes no totals: 366/1,128 exact rank tables and 45/1,128 exact suit tables, with zero wrong-back-on-unreadable matches. Publisher/helper hashes and both metric versions are retained. Neither the frozen reader nor inputs are retuned to improve the score.

## G. Latency decision

The user-facing criterion is submission to **complete validated structured state**, not first token. User-supplied gates: target p95 ≤2.5 s; 2.5–4 s conditional; >5 s offline/replay. A model taking 15–20 s would fail the live profile. No fixed API response time is promised by the documentation. Short observations and no explanations can reduce generation work; they do not replace measurement. [Official latency guidance](https://developers.openai.com/api/docs/guides/latency-optimization).

All API p50/p95/max, timeout rates and returned Fast-tier measurements are **not measured**. Local recorded p95 values are 239–419 ms internal processing during offline replay on a contended host. They exclude actual capture, encoding, upload, response validation and display; they cannot be compared to the API end-to-end target. The advisor's existing capture-based 2.2 s freshness expiry was not relaxed to accommodate an unmeasured model.
